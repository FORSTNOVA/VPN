# SmartVPN Windows and Android

This repository implements the SmartVPN Windows and Android client described in `SmartVPN_Windows_Android_开发文档.docx`, including shared Go scheduling logic, Windows TUN, and Android VpnService.

## Current scope

- Flutter Windows UI source for subscription URL, Mihomo executable, connect/disconnect, status, and latency of the active node.
- The connection screen can fetch and select subscription nodes without starting Mihomo or changing the Windows proxy. It defaults to a continuously checked automatic group, offers a fallback group, and still permits manual node selection.
- Announcement entries are filtered from selectable proxies. A sanitized subscription diagnostic view reports HTTP status/content type, query key names, URI counts, VMess transport/TLS, and WebSocket Host/Path presence.
- Go local service bound only to `127.0.0.1` on a random port. It creates a per-run random API token and generates a Mihomo configuration rather than accepting remote YAML as the local controller configuration. Every route requires that token except one: `GET /api/identify` answers with the app's name and whether its kernel is running, because a copy of this app has to be able to tell whether the machine's single system proxy setting is being served by another copy — another profile directory, a portable copy beside an installed one — and the other copy's token belongs to the other copy. The answer says nothing about the user, and the loopback binding means only processes running as this user can ask.
- Windows current-user Internet Settings proxy update with a per-user backup. On disconnect or normal app shutdown, values are restored only when they still match the values SmartVPN set; user changes made while connected are preserved.
- A downloaded subscription is saved only when it contains selectable nodes; an announcement-only reply cannot replace the last valid local profile. For `sub` links that return announcements, the client retries the Clash `cla=1` format and records which format worked. Mihomo reads the profile from a file and uses available local proxy and controller ports, so another client's port 7890 does not block connection. Credentials in the subscription URL are kept out of SmartVPN logs.
- Current routing imports supported domain and IP rules from the subscription. `DIRECT` and `REJECT` keep their meaning; a rule that names one of the subscription's own groups is mapped by what the group's name says it is for — a domestic service or an ad blocker becomes direct or refused, and anything else becomes `SmartVPN` — because a subscription's groups cannot be reproduced faithfully and proxying 抖音, B 站 or Apple's push and App Store services is the opposite of what their group exists for. The rules that decide a connection themselves are emitted first, and the configuration ends with `MATCH,SmartVPN`. Mihomo provides `url-test` and `fallback` groups using the subscription nodes; the automatic group is the default and measures itself every five minutes. On connection, SmartVPN confirms that at least one node reaches both YouTube and ChatGPT before enabling the Windows proxy. The UI checks the actual Windows proxy setting every 15 seconds and shows the active node as it changes.
- Domestic traffic stays domestic. A subscription names the services its author thought of and leaves the rest to the last rule, so without anything else every domestic site the list does not name — and every address reached without a name, and every app talking to a bare IP — is carried by the proxy and asked to answer from abroad, which arrives as a page that will not load rather than as an obvious routing mistake. SmartVPN therefore keeps the country's own address ranges and matches them before the catch-all: 9,600-odd IPv4 and IPv6 ranges, fetched from a source reachable from here (the kernel's own geo database is not used, because mihomo refuses to start when a `GEOIP` rule's database is missing and its default source is GitHub), verified to be an address list before it is written, cached for a week, and refreshed in the background so no connection ever waits on the download. A refresh that fails keeps the previous list, and a machine that has never fetched one connects without the rule and says so on the connection page rather than failing to connect at all. The kernel is asked once, with a two-range configuration of its own, whether it accepts a `rule-providers` entry of this kind; if it does not, the rules are left out and the reason is logged.
- The connection page reports that list in one line: how many ranges it holds, when it was fetched, whether the configuration the kernel is running actually carries them (a list fetched after the kernel started is ready but not in effect), and a button to fetch it again. Nothing about it is a setting: the alternative to sending domestic traffic abroad is not a matter of taste.
- The traffic page reads the kernel's own connection table, so what the tunnel carries can be checked rather than assumed. It shows the session totals, the rate over the last two samples, and the connections behind them: the process that opened each one, the destination, the rule that matched, the outbound that carried it, and its bytes and age. A connection carried by `DIRECT` is called out, which is the row that answers whether protected traffic really entered the tunnel. The list is read-only, is capped to the heaviest connections, and is polled only while the page is open. Naming the process needs the kernel's `find-process-mode: always`, which the generated configuration sets.
- Closing the window no longer ends the process. The close button asks whether to minimise to the notification area or to quit; hiding keeps the tunnel up, and the tray icon is the way back (left click), with connect/disconnect and quit on its right-click menu and the connection state in its tooltip. Quitting stops the local service first, so the Windows proxy settings are handed back instead of being left pointing at a closed port. When the icon cannot be registered the prompt drops the hiding option, because a hidden window with no icon would be a window with no way back. Windows 11 files a new icon under its hidden-icons menu, so the first hide also shows a balloon saying where the window went. The minimise button keeps its ordinary behaviour. Multiple app windows reuse the same local service.
- Several subscriptions can be saved and enabled as sources for one combined node list. Choose a prefix for each source if you want its nodes labelled, then use **一键合并更新** to fetch the enabled sources and build one Mihomo provider; duplicate names are made unique, and each source keeps its own last-good cache so one offline source does not discard the others. The combined list can be used as the active profile and refreshed on a schedule, or a single subscription can still be activated on its own. Changing source selection takes effect on the next merge, and switching profiles is refused while the kernel runs so the current node, region lock and verification data are not replaced underneath a live connection. A URL entered in the address field joins the saved list as well. Each remote source can refresh its remaining traffic independently while connected: SmartVPN reads the provider's `Subscription-Userinfo` response header and updates only that source's quota display, without fetching or replacing the active node profile. Providers that omit that header cannot report quota through this action.
- Nodes can also be pasted in one at a time: a `vmess://`, `vless://`, `trojan://`, `ss://` or `hysteria2://` link is parsed into a proxy object, stored separately from any subscription, and given its own provider file. The kernel therefore measures, health checks, region verifies and fails over on them exactly as it does on subscription nodes. A link that cannot be represented completely is refused with the reason rather than half-converted, a link that would duplicate an existing name is refused too, and a machine that has only pasted nodes and no subscription still connects.
- The check page works like the browser-based IP toolboxes it was modelled on: one button runs everything and every row carries its own verdict. It reports the exit addresses, where they are and who operates them (from an HTTPS geolocation service asked through the node, so the answer cannot be rewritten by the node), which resolver answered for a freshly generated name we just looked up and whether that resolver belongs to the same country as the exit, whether the node forwards datagrams and whether the address a STUN server saw is the same one the tunnel presents over TCP, and whether Google, YouTube, ChatGPT and Gemini are reachable. The exit probes use ipify with a Cloudflare trace fallback; a failed IPv6 lookup is shown as unavailable rather than treated as proof of a leak. Everything runs while disconnected as well, by starting Mihomo temporarily without changing the Windows proxy settings, and the whole report can be copied as text.
- The path monitor checks Google and YouTube on its configured interval. It watches Mihomo's connection table for access to enabled optional targets; recovery checks Google and YouTube first on each verified same-region node and checks optional targets only after both baseline sites answer. If the baseline stays available but optional targets are not all reachable, it restores the original node and retries after 30 seconds. If the baseline fails across the region, it prompts and automatically scans again after 30 seconds unless cancelled. GitHub, Claude, ChatGPT and Twitch are built in, and any URL can be added. Any site response, including 403 or 429, counts as reachable. The same monitor and UI logic run on Android.
- The speed test measures throughput through the node — the same path the browser takes, not a theoretical line rate — by pulling from several connections to Cloudflare's public endpoint at once, with the clock starting when the first byte lands so the handshake is not charged to the rate. The size is chosen on the page because it is spent from whatever the subscription allows: the selection is the download allowance, the upload is a third of it, and each direction is capped at ten seconds.
- The DNS row measures the resolver this machine's queries actually go through, which is only the whole-device answer in TUN mode: with the system proxy on, a browser may resolve names by another route entirely, and the page says so.
- Subscription downloads no longer assume another proxy client is listening on port 7890. They use a transport without an application-level proxy and fall back to the last valid cached profile when the network cannot fetch a fresh copy.
- Exit region verification walks the node list, switching the `SmartVPN` group to one node at a time and asking two independent IP-geolocation services for the exit address. Only nodes where both sources agree are marked `verified`; a single-source answer, a disagreement, or an unreachable node stays out of every candidate pool. Results are stored in SQLite and expire after 24 hours, after which the node must be re-verified. Verification runs in the background with progress in the UI, and it briefly changes the node that new connections use.
- A health state machine (`HEALTHY`, `SUSPECT`, `UNHEALTHY`, `COOLDOWN`, `RECOVERY`) runs while connected. Each sweep asks Mihomo for one bulk group measurement and folds it into the node in use plus every candidate of the locked region, so a single call keeps the whole pool's health and latency current. Mihomo only offers a per-group bulk delay endpoint: its per-proxy route cannot address the node names these subscriptions use, which all contain spaces, pipes or emoji. Two consecutive failures mark a node unhealthy; the switch to a standby respects a minimum dwell time and puts the failed node in cooldown. A sweep whose measurement cannot be taken at all counts as a failure of the node in use and leaves the candidates' earlier readings alone, and a note appears on the connection page when a sweep condemns the whole region while a real request still gets through, so a line that has gone dead becomes visible — and can still fail over to a known-good candidate — instead of leaving the node reported as healthy while every request times out. The six tunables are stored in SQLite, editable in the UI, and clamped to ranges the loop can actually run with. A sweep is not free: the bulk endpoint tests every node in the subscription, and mihomo's per-proxy route cannot address names containing spaces, pipes or emoji, so the whole group is the smallest unit that can be measured and the cadence is the price. It is 60 seconds rather than the 30 the design document suggests, because that document also says these values have to be calibrated on a real network — every probe is a connection from the user's own address, and a subscription that limits how many one user may open charges this client for all of them. The kernel's own provider health check is disabled for the same reason: it tested every node once a minute, continuously and regardless of what the client was doing, to maintain an `alive` flag that a sweep already refreshes (measured: it was one full pass of the subscription per minute before, and none after). What is left is one loop, and it is the one whose readings the failover decision actually uses.
- Region locking is opt-in and follows the node the user picks or the node in use. While a region is locked the `SmartVPN` selector is pinned to a concrete verified node of that region rather than left on an automatic group, because Mihomo's own url-test group would otherwise be free to leave the region. A connection is refused, rather than silently leaking, when the locked region has no verified node that reaches both YouTube and ChatGPT; if the region runs out of nodes later, the group is pointed at `REJECT` so protected traffic fails closed — but only once an independent probe agrees that traffic really cannot flow. That verdict comes from one bulk delay measurement, and a measurement can fail on its own: the kernel's test target, its resolver, or the delay API itself can break while the tunnel is perfectly usable. A region whose nodes are all reported dead while a request through the node in use still answers is a broken measurement, not a broken region, and blocking there would turn the app's own diagnostic trouble into the user's outage — which is what a sweep that condemned eleven nodes at once did, for seven minutes, in the field. So before protected traffic is dropped, one HTTPS request is made through the local port, the way an application makes it, to a host that is not the one the sweep measures; a captive portal cannot answer for it, and an answer means the connection is kept and the connection page says why nothing was failed over. Nothing leaks by waiting: the group stays on a concrete node of the locked region, and the region is still never crossed. The pinned node is kept while it stays reachable — switching is failure-driven, not a race for the lowest latency — and the lock survives disconnects, restarts and settings updates. With no locked region, node selection stays with Mihomo's own automatic groups.
- Node health, exit regions, and switch events are persisted in the service's directory (`%APPDATA%\SmartVPN`, or `SmartVPN-data` in a portable copy) as `smartvpn.db` (pure-Go SQLite). Switch events record the old node, the new node, the trigger, and the probe evidence, and can be reviewed in the UI.
- The connection mode is selectable: **system proxy** (M1 behaviour) or **TUN**, where Mihomo's own TUN inbound takes over the default routes so programs that ignore the system proxy are covered too. TUN needs an administrator token and `wintun.dll`; when either is missing the mode is reported as unavailable with the exact reason, and a connection attempt is refused before the kernel is started. The UI offers a download for `wintun.dll` and a relaunch-as-administrator button, which is the only way to gain the token — an already running process cannot raise its own privileges.
- `wintun.dll` is fetched from the official WireGuard build and is accepted only if the archive hash, the extracted library hash and its Authenticode signature all match, so a tampered download cannot reach the TUN data path. A local file can be named instead, and it still has to carry a valid signature. The library is installed next to the kernel's working directory, which is where the loader looks for it.
- TUN mode leaves the Windows system proxy untouched, and the same generated configuration adds a `dns` block with `fake-ip` plus `dns-hijack`, so name resolution goes through the kernel rather than the local resolver.
- The generated `dns` block excludes the subscription's own node hostnames from fake-ip and resolves them through `proxy-server-nameserver`. An outbound connection starts by resolving one of those names, and a fake answer sends the kernel's dial to an address inside the tunnel — the connection is captured back into it and no node can be reached. Node hostnames are validated before they are written into the configuration, since the subscription file is third-party input.
- The `dns` block resolves IPv4 names only (`ipv6: false`). Subscription nodes normally have an IPv4-only exit, while `auto-route` still points the IPv6 default route at the adapter; Windows prefers IPv6, so handing out AAAA records would begin every connection with a request the node cannot carry, and a direct-routed IPv6 packet would be captured by the tunnel as well. That combination is what makes a TUN connection look like a dead network rather than a slow one. The `tun` block itself is unchanged.
- `POST /api/tun/check` reports the TUN path: administrator token, the installed library, whether the virtual adapter exists and is up, whether the IPv4 and IPv6 default routes point at it, whether a freshly generated name resolves into the fake-ip pool, whether the node's own hostnames resolve to real addresses, and — the acceptance criterion — whether an ordinary connection with no proxy configured exits at the same address as the tunnel. When the two differ the check fails rather than claiming success. The IPv6 row reports the disabled resolution instead of an address.

TUN mode covers the whole device only through Mihomo's own TUN inbound; it is not a separate firewall, and per-application routing is still not implemented. Because the IPv6 default route also points at the adapter, a program that reaches an IPv6 literal directly still enters the tunnel and meets the node's IPv4-only exit; name-based traffic is unaffected because no AAAA records are handed out.

- The generated configuration refuses UDP on port 443, so a client that tries HTTP/3 falls back to TCP and TLS. When a node cannot relay UDP, those requests otherwise hang: an application whose login uses QUIC reports a failed request instead of retrying, which is what happened to a desktop client whose token exchange targets `auth.openai.com`. The rule sits between the rules that decide a connection themselves and the ones that hand it to the proxy: ahead of a `DIRECT` rule it would take HTTP/3 away from the domestic sites that serve it, and behind a proxy rule that rule would claim the datagram first, which is the hang the rule exists to prevent. Whether the node in use really carries UDP is measured on demand rather than assumed: the check page opens a SOCKS5 UDP association on the local mixed port and sends one DNS query through the node.

## Android

The Android half is the same Go service, linked into the application instead of started beside it, and the same Flutter pages. What differs is what the platform insists on.

- The service is a library inside the app, not a process. Since Android 10 an app may not execute anything in its private directory, and the only executables it has are the native libraries the installer unpacked; the kernel is compiled in as well, so there is nothing to exec and nothing to fetch at run time. `android.ps1` builds that library for the device's architecture first and the package around it second — `flutter build apk` alone produces a package that installs and then fails at the first call.
- The kernel is built with `-tags cmfa,with_gvisor`, and neither tag is optional. Without `cmfa` the kernel builds its own Android routing rules when its TUN starts, which means reading the system's package list — a file no ordinary app may open. The listener then fails, the interface it was given has nobody reading it, and every application on the device loses its network while the window reports a connection. With it, the kernel leaves routing to the VpnService that made the tunnel, which is where routing belongs. `with_gvisor` is needed because the generated tunnel uses the gvisor stack and `cmfa` drops it, which shows up as the kernel refusing to start the listener and saying so.
- The window talks to the same local API, on the same loopback address, with the same token. The address arrives over a method channel rather than on the service's standard output, and the service record is published in the profile directory as it is on Windows — `adb shell run-as com.smartvpn.client cat files/SmartVPN/service.json` reaches it, which is how a phone can be debugged from a desk.
- The tunnel's descriptor belongs to the kernel once it exists. The VpnService detaches it and hands it over, and the service closes it again only when no kernel ever took it. Android's file-descriptor checker aborts the process when native code closes a descriptor a `ParcelFileDescriptor` still claims, and the kernel closes the descriptor it was given when it stops.
- This app is excluded from its own tunnel, and that is deliberate rather than convenient: a subscription has to be fetched before there is any node to fetch it through, and the kernel's connections to the proxy servers are the tunnel's upstream — they cannot be carried by what they carry. Every socket the kernel dials is protected as well, so the guarantee does not rest on the exclusion alone.
- Because of that exclusion, Android still hands this app the VPN's resolver address, which it cannot reach: every lookup would be a timeout rather than a failure, and a checks page would hold the service for minutes. The service therefore resolves through resolvers of its own, the same two the kernel is configured with. The DNS-takeover row is reported as unmeasurable here rather than as a pass, because from inside an app that is deliberately outside the tunnel there is nothing to measure.
- A tunnel must never outlive the kernel. If the kernel dies, the service stops the VpnService; if a connection fails to come up, the window takes the tunnel down. An interface with nobody reading it is what a device with no network looks like, and it is the worst state this app can leave behind.
- The kernel's tunnel listener is checked before a connection is reported as up: the kernel can be answering on its control port with its tunnel already failed, and only its log says so.
- Locking a region while connected binds the connection that is running, not only the next one. The group is moved to the best candidate of the new region, or blocked if there is none, because a window that says the region is locked while traffic leaves from somewhere else is the one thing the lock exists to prevent.
- The connection mode is `vpn` and there is nothing to choose: the system's VpnService carries everything, the app asks for the user's authorisation when it connects, and a notification with a disconnect action is how a running connection is visible. The single-instance arbitration, the system-proxy setting and `wintun.dll` have no counterpart here, and the subscription URL is sealed with a key from the Android keystore, which the app can use and cannot read — a copy of the profile taken off the device is not a copy of the subscription.
- The tunnel is described by the system and read on demand: the interface, the routes on it and the resolver it points at. The system fills a tunnel in over more than one step, so a description taken once, when it is established, can say there are no routes while the tunnel is carrying everything.
- Per-application routing is not implemented, which is the design document's own warning: the VpnService decides which applications are inside the tunnel, but giving different applications different nodes inside it needs a per-connection owner that this app does not have.
- The pages are the desktop ones, made to fit a phone: below 700 logical pixels the rail becomes a drawer, the control rows that would not fit move their buttons to the next line, the region and node rows put their latency and badges under the name instead of beside it — a name squeezed to three characters is the one thing on the row the reader needs — and a dialog is as wide as it was designed to be or as the screen is, whichever is smaller. A test renders every page at phone width and fails on an overflow; the rows that only exist with data, which a harness without a local service cannot produce, were checked on a device.

Colours come from one token set in `lib/tokens.dart`: a single accent colour, four signal colours and three radii. Depth comes from the tinted rail and hairline separators, with a shadow reserved for the connection surface, and every number is set in tabular figures so a column of changing values does not shift. Selecting a node moves the region lock whether or not the kernel is running. The smallest window offered is 900×600 logical pixels, enforced through `WM_GETMINMAXINFO`. The close button asks before acting, and the notification-area icon is what keeps a hidden window reachable — see the tray note above.

The targeted path monitor checks Google and YouTube at the configured interval. It watches Mihomo's live connection table for access to enabled optional targets; once access is seen, recovery checks Google and YouTube first on each verified node in the selected region, and checks the optional targets only when both baseline sites answer. If the baseline works but some optional targets fail, it keeps the original node and retries those targets after 30 seconds. If the baseline fails across the region, it shows a 30-second prompt and then scans the region automatically unless the user cancels. This keeps routine checks to two sites while preserving the user's region and node when only a specific destination is affected.

## One service at a time

The kernel and the proxy are meant to outlive the window, so a service left running by an earlier launch would otherwise still be holding its own Mihomo — and no window would be able to reach it. The service therefore publishes its address, port and per-run token to `service.json` in its directory (mode 0600) and a later launch asks that address first:

- The probe has to be answered with the published token, so a port that happens to belong to an unrelated process is never mistaken for ours, and a record left behind by a crash simply fails the probe and is replaced.
- A live service is **reused** when it holds at least the privilege of the new instance, and the new process prints the existing address and exits, so the app talks to the service that is already running instead of starting a second one.
- A service whose binary was replaced by a rebuild is **taken over** on the next launch while it is idle, so a new build takes effect without stopping anything by hand. A service that is still carrying a connection is left running until it disconnects.
- When the new instance holds a **higher** privilege — a relaunch as administrator — it asks the old service to shut down and takes over, so TUN is not blocked by an unelevated service that was still running.
- A clean shutdown removes the record; a forced one leaves it, which the next launch recovers from by itself.

A service started by a build older than this change publishes no address, so it cannot be discovered and will coexist with a new one until it is stopped once (Task Manager as administrator, or a reboot).

That record is per profile directory, so it covers the copies that share one — an installed copy relaunched, or a window opened twice — and says nothing about a copy running from a different directory. A packaged copy unpacked beside an installed one keeps its data in its own folder and therefore runs its own service, and the two do not see each other. What they do share is the machine's single system proxy setting, so that is what they arbitrate over instead. The copy that turns the setting on publishes a record beside it, in the registry the setting already lives in, which is the one place every copy can read no matter where it was unpacked. The record names that copy's profile directory, the port the setting points at (the kernel's) and the port its own service answers on. The service port has to be in the record because the setting cannot carry it: the address in the setting belongs to mihomo, which knows nothing about this app's routes. Before connecting in system-proxy mode, and before the startup restore of a previous run's settings, this service reads that record, and when it names another copy whose service still answers `GET /api/identify` on the recorded port, it refuses to connect rather than silently taking the setting away, naming TUN as the way out because TUN does not use the setting at all. The record is removed when the setting is handed back, and only by the copy it names, so one copy's release cannot erase another's claim. Another proxy client's setting is not ours either: it is taken over and handed back unchanged on disconnect, as it always was. Nothing here protects the TUN adapter, which a second copy in TUN mode would also collide over; that copy reports a kernel that did not come up rather than anything about the reason.

## Build on Windows

VS Code is the editor; it does not include the compilers. This workspace has portable Flutter and Go SDKs under `.tools`; the VS Code tasks use them directly. Flutter's Windows setup also requires Visual Studio (separate from VS Code) with the **Desktop development with C++** workload. See the [Flutter Windows setup guide](https://docs.flutter.dev/platform-integration/windows/setup) and [Go installation guide](https://go.dev/doc/install).

The repository root contains VS Code tasks to generate the Windows runner, fetch packages, build both components, copy the proxy helper, and launch the result. Open this repository folder in VS Code, then select **Terminal → Run Task → SmartVPN: Run Windows MVP**. The first task run generates the Flutter Windows runner.

Equivalent PowerShell commands:

```powershell
cd frontend
& ..\.tools\flutter\bin\flutter.bat create --platforms=windows .
& ..\.tools\flutter\bin\flutter.bat pub get
& ..\.tools\flutter\bin\flutter.bat build windows --release
cd ..\backend
$env:GOCACHE = (Resolve-Path ..).Path + '\.tools\go-cache'
$env:GOPATH = (Resolve-Path ..).Path + '\.tools\gopath'
$env:GOPROXY = 'https://goproxy.cn,direct'
$env:GOTOOLCHAIN = 'local'
& ..\.tools\go\bin\go.exe build -ldflags="-s -w" -o ..\frontend\build\windows\x64\runner\Release\smartvpn-service-current.exe .
Copy-Item .\proxy.ps1 ..\frontend\build\windows\x64\runner\Release\proxy.ps1
```

`GOPROXY` points at a mirror because the default module proxy is unreachable from this network; `GOTOOLCHAIN=local` keeps the build on the pinned SDK instead of fetching a newer toolchain.

The service is built with `-ldflags="-s -w"` on purpose. 火绒 (Huorong) removes an unstripped build of this size as `代码混淆器(HEUR:VirTool/Obfuscator.a)` the moment it is written, at any path; the same code built without the symbol table and DWARF data is left alone. Nothing else needs those tables — a Go panic report keeps its file and line numbers either way — so the release and debug builds are both stripped. If a scanner still objects, add the build output directory to its trust list rather than dropping the flag.

The runner is compiled with `/utf-8`. It carries the Chinese text of the tray menu, its tooltip and its balloon, and without the flag MSVC reads those sources in the machine's ANSI code page (936 here) and the literals come out mangled — which shows up as `C2001: newline in string literal` rather than as anything about encodings. `package.ps1` is saved with a UTF-8 byte-order mark for the same reason: it names a Chinese file, and Windows PowerShell 5.1 reads a BOM-less script in the ANSI code page.

## Portable package

`Terminal → Run Task → SmartVPN: Package portable zip` (or `powershell -ExecutionPolicy Bypass -File package.ps1`) builds both halves and writes `dist\SmartVPN-<version>-portable.zip`, about 37 MB. Unzipping it produces one folder that runs where it is unpacked:

```
SmartVPN-0.1.0\
  smartvpn_windows.exe            the window
  flutter_windows.dll, data\      what the Flutter runner itself needs
  native_assets.json              what that runner reads at startup
  smartvpn-service-current.exe    the local service
  proxy.ps1                       the helper the Windows proxy is set through
  mihomo.exe, wintun.dll          the kernel and the TUN library
  使用说明.txt                    a short start-here note
  LICENSES\GPL-3.0.txt, NOTICE.txt
```

It is a zip rather than a self-extracting executable on purpose: a single-file launcher is exactly the shape scanners flag, and this package already has enough of that shape.

The kernel and the TUN library are not built here, so the script takes them from `%APPDATA%\SmartVPN`, where a working installation keeps them; with neither present it refuses to package unless `-AllowMissingKernel` is passed, because a package without a kernel cannot connect at all.

The package is self-contained. It carries `portable.txt` beside the executable, and that marker moves everything the service writes — settings, node cache, logs, the database, the subscription URL, the proxy backup — into `SmartVPN-data` in the same directory instead of the user's profile. The kernel and the library are run where they lie rather than copied in, so the folder stays around 100 MB and can be moved, copied or deleted as one unit, and the 配置目录 row on the connection page shows which directory is in use.

Two fallbacks keep that from being fragile: a copy that carries the marker but sits somewhere it cannot write goes back to the profile and says so in `service.log`, and a copy without the marker has a bundled `mihomo.exe` or `wintun.dll` adopted into its own directory on first run. The kernel's location is never stored as a default — an empty field means the copy that came with the package, otherwise the one in the profile, resolved each time it is used so a folder that is moved keeps working.

Redistributing the kernel is a licensing obligation, not just a convenience: Mihomo is GPL-3.0, so the package carries the full licence text and a notice naming the component, its version and where its source lives, and the same is recorded for `wintun.dll` from WireGuard LLC.

Run the test suites with `Terminal → Run Task → SmartVPN: Run all tests`, or directly:

```powershell
cd backend; & ..\.tools\go\bin\go.exe test ./...
cd ..\frontend; & ..\.tools\flutter\bin\flutter.bat test
```

For a Debug build, copy `smartvpn-service-current.exe` and `proxy.ps1` beside the Debug runner executable instead. Place the Mihomo Windows executable at `%APPDATA%\SmartVPN\mihomo.exe`, or enter its full path in the UI; leaving that field empty means exactly that directory. The service owns that default — it is the same directory as the database, the profile and `wintun.dll` — and reports the path it will use, so the interface never computes one of its own. On first connection, paste a Mihomo-compatible subscription URL. The client generates its own local configuration; it does not import arbitrary remote YAML as the client configuration.

Mihomo logs and generated settings are stored under the service's directory — `%APPDATA%\SmartVPN`, or `SmartVPN-data` beside the executable in a portable copy — and the service keeps its own log in `service.log` beside them — the kernel's log records nothing about a refused failover, an unmeasurable sweep or a proxy restore, and the app does not display the service's output. Logs are the files a user pastes into a bug report, so a subscription URL reaches neither of them: everything the service logs passes through a redactor that strips the URLs this profile knows about, and the kernel's own log is cleaned on every start, because an earlier build configured the kernel with the subscription URL as an HTTP provider and every failed pull wrote the URL, its token and all, into mihomo.log. That log is also trimmed to its newest 8 MB on each start, which bounds both the disk it takes and the work the cleaning does. service.log is not rewritten because the service holds it open for its whole life, and replacing a file a live process has open sends that process's later lines into the removed one. The subscription URL is stored locally in that directory and may itself contain credentials, so protect the Windows account. Subscription diagnostics hide query values, server addresses, UUIDs, and raw response data. A forced termination of both the UI and service cannot run cleanup code; the next service launch attempts to restore any saved proxy backup.
