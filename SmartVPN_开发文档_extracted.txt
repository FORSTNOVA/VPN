SmartVPN Windows 与 Android 开发文档

版本 1.0　｜　2026 年 9 月 24 日　｜　目标：独立客户端，Mihomo 内核

本文将双平台需求转化为模块边界、实现顺序和可验证的交付标准。先交付 Windows 系统代理版，再完成严格地区保护所需的 TUN 路径，最后移植 Android。具体版本和接口以实施时锁定的依赖版本为准。

1 项目范围

项目

要求

平台

Windows 10/11；Android。无需 iOS 代码与构建流程。

核心功能

订阅导入与更新、出口地区识别、同地区故障切换、测速、网站分流、应用分流、流量和连接监控。

保护规则

地区锁定以实测出口地区为准。未验证或冲突节点不进入严格锁定候选池；同地区耗尽时阻断受保护流量并显示告警。

交付范围

Windows 系统代理 MVP → Windows TUN 与严格保护 → Android VpnService。

4 节点发现与地区锁定

导入 Mihomo YAML 或 HTTP(S) 订阅后先解析与校验，再映射到内部节点。名称中的国家标记仅作候选提示。通过该节点访问可信出口查询服务，记录实际出口 IP 与地区；可用第二数据源交叉核验。入口服务器的地区不能替代出口地区。

严格锁定采用 fail closed：仅 verified 且出口地区等于锁定地区的节点可被自动或手动选入。未知、过期或冲突状态节点须重新验证。当前组没有可用节点时，规则明确指向 REJECT，防止落到 DIRECT、其他地区组或订阅提供的默认兜底。系统代理版仅保护使用系统代理的应用，不能称为全设备断网保护。

5 健康检测与故障切换

状态

进入条件

动作

HEALTHY

探测成功、连接正常

保持节点；周期检测

SUSPECT

一次失败或疑似超时

立即检测当前节点及同地区备用节点

UNHEALTHY

连续失败达阈值并由独立探测确认

切换至验证过的同地区候选节点

COOLDOWN

切换后的故障节点

暂停候选资格，记录冷却截止时间

RECOVERY

冷却结束且后台连续成功

恢复候选资格，不立即抢回当前连接

初始建议：连接检测 3 秒、巡检 30 秒、2 次失败确认、60 秒冷却、30 秒最短驻留、3 次成功恢复。这是可配置参数，必须在真实网络中校准。切换通常只影响新连接；现有 TCP 会话可能断开，不能自动重放有副作用的请求。

Mihomo 延迟接口可以检测节点可用性，连接与流量接口可以辅助监控，但不等于所有真实连接超时事件。首版以主动探测、内核可得连接状态及网络变化事件触发；精确的每连接失败通知若控制 API 不足，需要评估内核扩展。

6 分流与订阅

网站规则按域名优先、IP 规则补充，匹配到独立 PolicyGroup。Windows 的应用规则在 TUN 阶段通过可验证的进程识别能力实现。Android 的 VpnService 允许按包名决定哪些应用进入 VPN；若要让不同应用在隧道内使用不同节点，仍需可靠的每条流量归属机制，必须单独验证，不可将允许名单当作完整的应用级路由。

订阅定时刷新必须限制响应大小和超时、验证配置结构、隔离用户私密 URL、避免远程配置覆盖本机控制接口、DIRECT 禁令与地区策略。解析失败保留上一份可用配置并提示错误。

7 平台实施

7.1 Windows

第一阶段以独立 Mihomo 进程和系统代理工作。启动前检查配置；崩溃后检测进程与代理设置；退出时仅恢复由本客户端修改的设置。后续增加 TUN、DNS 与 IPv4/IPv6 路径检查，验证无绕过。严格全设备保护必须在 TUN 与系统路由或防火墙保护通过后才能在 UI 中声明。

7.2 Android

Kotlin 负责 VpnService 授权、TUN 创建与前台服务生命周期；代理出站套接字需避免再次进入 VPN 造成回环。验证断网、切换 Wi-Fi 与移动网络、后台恢复、省电限制、IPv6 与 DNS。Go/Mihomo 以可调用库形式适配，接口设计预留配置、TUN fd、网络变化、状态事件和安全关闭。

9 测试矩阵

至少覆盖：节点故障及恢复；同地区全部不可用；地区信息过期或冲突；订阅更新移除当前节点；多个策略组互不影响；DNS、IPv4 与 IPv6 出口；进程异常退出；睡眠唤醒；Android 后台与 Wi-Fi/移动网络切换。将“出口地区不变”“受保护流量不直连”作为可观测断言，并记录网络抓包或测试服务结果。
